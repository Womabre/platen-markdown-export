# Frontmatter, templates and the source document

Which keys the exporter reads, where defaults come from, how a document is scaffolded, and the only code that writes back to it. Reached from [`CLAUDE.md`](../../CLAUDE.md). Domain terms are in [`GLOSSARY.md`](../../GLOSSARY.md).

## Frontmatter keys

**Frontmatter keys** (`frontmatter-keys.ts`) — `FRONTMATTER_KEYS` is the one list of every key the exporter reads, with a description and a JSON Schema fragment each. Two things are built from it: `unknownKeyWarnings`, called once from `extractFrontmatter`, and `--frontmatter-schema` (committed as `schema/frontmatter.schema.json`, which a test compares against the generator, so regenerate it with `node dist/index.js --frontmatter-schema > schema/frontmatter.schema.json` after editing the table). **Adding a key to `extractFrontmatter` means adding it to the table**: `frontmatter-keys.test.ts` scans `extractFrontmatter`'s `at('…')` calls and fails on any undeclared one, since an undeclared key would be reported as a typo in every document using it. The warning is a near-miss detector, not an allowlist: documents carry other tools' keys (`tags`, `marp`, `draft`), so only a key that folds to one of ours (case, spaces, `_`/`-`) or sits within a small transposition-aware edit distance is reported, with a tighter limit for short keys because two edits turn `tag` into `Lang`. `Document Info` and `Variables` are never checked: their keys are the author's own.

## Frontmatter defaults

**Frontmatter defaults** (`projectconfig.ts` `discoveredFrontmatterDefaults`, `frontmatter.ts` `withDefaults`) — `frontmatterDefaults` in config files, nearest file winning per key (case-insensitive), `Variables` merged per name. Applied to the parsed attributes inside `extractFrontmatter` only, and the source write-back parses the document's own frontmatter rather than taking `extractFrontmatter`'s result, so no stamp, release or TOC cleanup can write a default into the document, and `unknownKeyWarnings` runs on the document's own keys while defaults are checked where they are read. `NOT_DEFAULTABLE` keeps out the revision machinery and `Title`, plus `Mode`/`Export On Save`: the extension decides export-on-save from the document's text, so a default `Mode` would export from the CLI and never on save. Known gap: the live preview (`preview-plugin.ts`) selects its stylesheet from the document text and does not see defaults.

## Question-answering surfaces

**Question-answering surfaces** — `--inspect` (`describeDocument` in `index.ts`) prints the *resolved* frontmatter as JSON and stops: reads the document, renders nothing, writes nothing, and returns before the theme is loaded. `--list-themes --json` / `--list-styles --json` do the same for the theme catalogue, and `--check-setup --json` (`setup-status.ts`) for the runtime dependencies — the extension builds its one install question from it. That one is deliberately its own flag rather than `--setup --dry-run`: the extension asks it of whatever CLI it resolves, an older CLI ignores `--dry-run` next to `--setup` and would install everything on what was meant to be a question, while an unknown flag is refused and reads as "cannot tell". They exist because tooling has to know things about a document *before* acting on it — the VS Code extension asks whether the revision it is about to release already carries a note, and only prompts when it does not. Without them the editor would need its own YAML reader and theme resolver, which is a second answer to "what does this document say" living one refactor away from disagreeing with the first. `--inspect` returns the resolved view on purpose (`Mode: pdf, html` normalised, `resolveRevision`'s precedence applied, `isReleasedStatus` so `Vrijgegeven` counts) — a caller reading the file itself would have to re-implement all three.

## Source write-back

**Source write-back** (`source-writeback.ts`) — the only code that writes to the source document; the terms are in `GLOSSARY.md`. `openSourceDocument(file, { writes, release, note })` reads the file once and returns a handle: `content` (what the export renders, already stamped), `outputLanded()` (the first output earns the date stamp and TOC cleanup), `allOutputsLanded()` (the release, so every output carries the pre-release revision) and `written` (for `--watch`). Three rules live there and nowhere else. **Only what the document says**: it re-parses the document's own frontmatter and takes no `FrontmatterData`, because that one has `frontmatterDefaults` applied; a default Author once reached a new Revisions row this way. **Keys match the way the reader matches them**, case-insensitively, keeping the document's own spelling; the writer once knew only `Status`/`status`, so `STATUS: Released` was bumped but never reset. **One baseline**: the handle remembers what it last read or wrote, and every write is a compare-and-swap against it, skipped with a warning when another process changed the file. A release that cannot happen (Status not released, no Revisions rows) is reported when the handle opens, before the render. Test it through the handle on temp files (`src/tests/source-writeback.test.ts`), not through its private helpers.

## Release notes

**Release notes** — `--release-note <text>` sets the `Remarks` of the **outgoing** revision: the current last `Revisions` row, describing the work being signed off, which is the row the cover's revision table shows. Inside the source write-back, `setLastRevisionRemarks` must run *before* `appendRevisionEntry`, or it would fill in the fresh row `--release` appends for the next revision — in which nothing has happened yet. It is a usage error without `--release`, because a note with nothing to attach it to would otherwise vanish while the export looked like it succeeded. Both frontmatter shapes are handled and the document's own key casing is kept.

## Scaffolding

**Scaffolding** — `frontmatterTemplate(today, answers?)` is the one implementation of answers → frontmatter, reached from the CLI by `--init [--answers <file.json>]` and from the extension's new-document wizard through that same flag. Answered values go through `yamlScalar`, which quotes only when YAML requires it: the default `--init` output stays byte-identical (people read it as documentation), while a title with a colon, an author with a comma inside a flow mapping, or a status of `No` are all protected. Answers arrive in a *file* rather than on the command line because a title and an author are free text a person types, and putting that through argv quoting on three platforms is a bug waiting to happen. **The extension keeps its own copy of the placeholder template** (`vscode-extension/src/core.ts`) — that is deliberate, guarded by a key-comparison test in `frontmatter.test.ts`, and the reason is that `insertFrontmatter` edits an *unsaved editor buffer* and must keep working when the CLI cannot be resolved. The wizard, which creates a real file, goes through the CLI instead.

## Templates

**Templates** (`templates.ts`, `templates/`) — a template is a folder with `template.md` (+ optional `template.json` description); roots are `--template-path` → `EXPORT_TEMPLATE_PATH` → `templatePaths` in config files (walked up from the working directory, since no document exists yet) → the `templates/` folder of every discoverable theme (`themeTemplateRoots`, so `applyThemeRoots` must run before any template lookup, as it does in `parseArgs`; a shadowed theme contributes none) → built-in `templates/`, external shadowing built-in by name. `scripts/run-tests.js` points `XDG_CONFIG_HOME` at an empty folder, because the developer's own user config adds roots and changes every listing. **`renderTemplate` never writes YAML of its own**: it starts from `frontmatterTemplate(today, answers)` and merges the template's top-level blocks in as *text* (`splitBlocks`), so quoting stays `yamlScalar`'s job and the template's comments survive. `Title` and `Revisions` are always the scaffold's, `Document Info` only gains the template's extra labels, an answered key beats the template's block (`ANSWER_KEYS` maps answer fields to keys — extend it when `FrontmatterAnswers` grows), and unknown keys are appended. Only `{{Title}}`, `{{Author}}` and `{{Date}}` are filled in the body; every other `{{Name}}` must survive for `Variables`. `templates/` ships in the npm package (`files`) and is copied by `vscode-extension/scripts/bundle.js`; a built-in template test exports each one with `--strict`, so a template that warns fails the build. The extension renders by the template's *file* path (`--template <file>`), not its name.
