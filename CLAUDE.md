# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A TypeScript CLI that converts Markdown (or HTML) to print-quality PDF — and optionally a self-contained HTML file — via [WeasyPrint](https://weasyprint.org/), with swappable branding: cover pages, running headers/footers, revision tables, and a rebuilt table of contents. Branding lives in **themes** (folders under `themes/`: `default` is the brand-neutral fallback and is aligned with the Marp default theme; `gaia`/`uncover` mirror those Marp themes; `github` mirrors GitHub's rendered-markdown look; `modern` is the full brand-package showcase — fifteen fruit-named palettes, per-style hero photography, a `logos` map and `paletteRoles`; plus ports of the mixu/markdown-styles layouts built on the shared `default` base CSS, overriding only colours/typography/background). Layouts that share a prefix are collapsed into one theme whose **styles** carry the per-variant fonts/background/colours (`jasonm23` → Dark/Foghorn/Markdown/Swiss; `mixu` → Book/Bootstrap/Bootstrap2col/Gray/Page/Radar; `solarized` → Dark/Light); the remaining single-layout ports (`bootstrap3`, `markedapp-byword`, `roryg-ghostwriter`, `witex`) stay standalone. There is no vendor-specific brand theme in the repo — the tree is genericised, and `modern` plus the `themes/acme-logo-*.svg` marks are the placeholder brand. Within a theme a per-document **style** picks the variant (cover gradient plus, where defined, its own `fontFamily`/`background`/`cssVars`/`fontImport`). Entry point is `dist/index.js` (built from `src/index.ts`); the CLI is exposed as `platen-markdown-export`.

## Commands

```sh
npm run check              # every gate CI runs, in CI's order — run before pushing
npm run build              # tsc → dist/ (incremental; must run before tests or CLI use)
npm run watch              # tsc --watch
npm test                   # pretest builds first, then: node scripts/run-tests.js
npm run lint               # eslint src
npm run verify:pdf         # build, then export a real PDF via WeasyPrint and assert its page tree
npm run check:versions     # root, vscode-extension, bundled/ and both lockfiles must agree
npm run version:set -- X.Y.Z   # set the version in every place that has to match
node dist/index.js --setup # install WeasyPrint + Playwright Chromium if missing
```

`npm test` never runs WeasyPrint, Chromium or the network — that is deliberate, and it is why `verify:pdf` exists as a separate check (CI runs it as its own job, on `test-fixtures/pipeline/document.md`, the same network-free fixture the HTML golden test uses).

Run the CLI during development against `dist/` (it has no transpile-on-run):

```sh
node dist/index.js [options] [stylesheet.css] <file.md|file.html>
node dist/index.js --mode pdf,html --no-bump "themes/default/sample default.md"   # both outputs, no source mutation
```

Run a single test file (tests are plain `node --test`, no framework):

```sh
npm run build && node --test dist/tests/markdown.test.js
node --test --test-name-pattern="includes" dist/tests/markdown.test.js   # filter by test name
```

Tests compile from `src/tests/*.test.ts` to `dist/tests/`; always rebuild before running or you'll test stale output.

`npm test` goes through `scripts/run-tests.js`, which hands `node --test` an
explicit list of files. That is not ceremony: `node --test dist/tests/*.test.js`
relies on the shell expanding the glob, which `cmd.exe` does not, and
`node --test dist/tests` works on Node 20 and 26 but fails on 22 with
MODULE_NOT_FOUND. An explicit file list is the one spelling every supported
version accepts, and it keeps the coverage flags out of shell quoting. Running a
single file by path (above) is unaffected.

## Runtime requirements (not npm-managed)

- **WeasyPrint** — the PDF engine, an external binary discovered by `bootstrap.ts` (`findWeasyprint`) at known install paths, not via PATH. PDF modes fail with exit code 4 if it's missing. On Windows, `installWeasyprintWindows` downloads WeasyPrint's standalone `weasyprint-windows.zip` release asset (a PyInstaller build with Pango/Cairo/GDK-Pixbuf/GObject statically bundled — no Python or GTK runtime needed) from a **pinned version whose SHA-256 is checked before extraction** (`WEASYPRINT_WINDOWS_ASSET`, `verifyChecksum`) — the `/releases/latest/download/` alias it used to fetch was unverifiable, since whatever bytes arrived were extracted and run with nothing to compare them against. It falls back to `installWeasyprintWindowsViaPip` (Python + pip + separately-installed GTK runtime) only if that download fails. `runBootstrap` also smoke-tests the resolved binary with `weasyprint --version` (`verifyWeasyprintRuns`) so a broken native-library load surfaces at `--setup` time, not mid-export.
- **Playwright Chromium** — only for rendering Mermaid diagrams (headless). `playwright` itself is an **optionalDependency**: it is a whole browser-automation library carried for one feature, and `mermaid.ts` already `await import`s it lazily. An install without it is a supported state — `isModuleNotFound` distinguishes a missing *package* from a missing *browser*, because the two need different commands to fix. Note `--omit=optional` is not a way to opt out: it is not package-scoped, and sharp ships its platform binaries as optional deps, so it breaks image handling instead.
- **draw.io desktop app** — only for rendering `.drawio` diagram references, discovered by `drawio.ts` (`findDrawioCli`) at known install paths/PATH; `bootstrap.ts`'s `ensureDrawio` installs it via winget/Homebrew-cask/snap alongside WeasyPrint and Chromium.
- **Web fonts** — optional, and currently unused: every shipped theme has an empty `fonts[]` and relies on system font stacks or a style-level `fontImport`. The capability remains in `theme.ts`'s `resolveFonts`: a `fonts[]` entry carries either a literal `url` (fetched and base64-embedded into the PDF) or an `env` naming an environment variable that holds the URL, for a theme whose font is behind a licensed link that shouldn't be committed. Adding a font to a theme therefore needs no code change — only a manifest entry, plus an `@font-face` in the theme's CSS for the HTML export.

## Architecture

The whole program is one async `main()` in `src/index.ts` that orchestrates a linear pipeline of string transformations on an HTML document. Each `src/*.ts` module owns one stage and exposes pure-ish functions plus the CSS it injects (modules export both their logic and their `*_CSS` constants, which `index.ts` assembles into `<head>`).

**Pipeline shape** (`index.ts`):

1. **Markdown → HTML** — `markdown.ts` configures markdown-it with all the plugins (katex, anchor, attrs, container, footnote, github-alerts, task-lists, abbr) plus custom rules for includes, admonitions, draw.io image syntax, and hex color chips.
2. **Frontmatter** — `frontmatter.ts` parses YAML frontmatter (case-insensitive keys) and, unless `--no-bump`, mutates the *source file*: stamps revision dates and bumps the revision after a `Released` export. This source mutation is the main reason `--no-bump` exists for CI.
3. **Shared heavy preprocessing** (`renderDiagramsAndImages`) — runs **once** even when both PDF and HTML are requested: Mermaid rendering (`mermaid.ts`, headless Chromium), Graphviz rendering (`graphviz.ts`, a WASM build of Graphviz — `@hpcc-js/wasm-graphviz` — with no browser, no network, and no external binary), infographic rendering (`infographic.ts`, AntV Infographic's own SSR entry point — see below), and image inlining (`images.ts`, which converts/raster-compresses via `sharp`). draw.io is *not* done here — it's rendered per-mode because PDF wants PNG and HTML wants dual-theme SVG (`drawio.ts`).
4. **Two divergent finishing pipelines**, both ending in TOC injection + rebuild (`html.ts`):
   - `buildHtmlPipeline` → PDF: full cover page, page CSS with running header/footer, fallback fonts, then handed to WeasyPrint.
   - `buildHtmlExportPipeline` → standalone HTML: a lighter banner instead of a cover, dark-mode CSS, body marked `class="html-export"` so layout CSS can scope to it.
5. **WeasyPrint export** (`weasyprint.ts`) — the processed HTML is served **from memory** over an ephemeral **localhost HTTP server** (not file://) rooted at the document's directory, so relative asset references still resolve; `execFile`s the WeasyPrint binary against `http://127.0.0.1:<port>/<token>/...`. Nothing is written next to the user's document — `--mode debug` is the sole exception, writing an inspectable copy on purpose.

**Performance-shaped ordering matters**: the cover page and fallback-font fetches are kicked off as promises *before* the heavy diagram work so they overlap with Mermaid rendering. The shared preprocessing exists specifically to avoid doing Mermaid/image work twice in `--mode pdf,html`. Preserve this overlap when editing `main()`.

**Infographics** (`infographic.ts`, `infographic-worker.ts`, `infographic-svg.ts`, `infographic-icons.ts`) — three rules, each learned the hard way. **The library runs in a worker thread**, because its SSR DOM shim assigns `window`, `document` and forty-odd DOM constructors onto `globalThis` and never removes them; in the main process every other library would believe it runs in a browser for the rest of the export, and of a `--watch` session. `src/tests/infographic.test.ts` asserts the main thread stays clean. **Its raw SVG does not survive WeasyPrint**: all text is HTML inside `<foreignObject>`, which WeasyPrint does not draw, so `infographic-svg.ts` rebuilds each as native `<text>` (pure string work, measurer injected). **Every request the library makes is proxied to the main thread** — the worker replaces `globalThis.fetch` *before* importing the library, which captures it at import time — and `decideIconRequest` decides it under `--infographic-icons` (`iconify` default / `weavefox` / `none`). That setting is machine-level only (flag, `EXPORT_INFOGRAPHIC_ICONS`, machine-scoped VS Code setting) and must never become a frontmatter key: a received document must not be able to opt the machine into sending its text to Ant Group's servers. Iconify icons are cached in memory only — their URLs are not versioned, so the disk-cache rule for unpinned remote assets applies. **A theme font the library names is bundled, not fetched** (`infographic-fonts.ts`, `assets/fonts/`): the `hand-drawn` theme's `851tegakizatsu` would otherwise come from Ant Group's CDN. Its `@font-face` goes inside the SVG — a browser renders an `<img>` SVG as its own document, so the page's CSS never reaches it, while WeasyPrint accepts either — and the family is **quoted** in every `font-family`, because a CSS identifier may not start with a digit and unquoted `851tegakizatsu` invalidates the whole declaration (Chrome then falls back to its default serif, not to Arial). Wrapping is measured with that font's own measury metrics. When checking rendered output, rasterise PDFs with macOS Quartz (`sips -s format png`) rather than poppler: poppler's `pdftoppm` fails to draw WeasyPrint 70's SVG gradients — every bar of a column chart vanishes — while Preview and Quartz render them correctly.

**Export plan** (`plan.ts`) — the decision half of `main()`, with no I/O: theme-name precedence (`--theme` → `Theme` → `EXPORT_THEME` → default), stylesheet choice and its summary label, mode resolution, DPI, and the output paths. `resolveExportPlan` throws `ExitError` for usage errors and resolves both output paths **up front**, so a bad path fails before the expensive diagram work rather than after it. It is a separate module because the overwrite guard in `outputPathFor` — which stops an export writing over the user's own source document, reachable with an `.html` input in html mode and no revision — is a data-loss guard that had no test while it was a closure inside `main()`.

**Export execution** (`executeExport` in `index.ts`) — the doing half, split from `main()` for the same reason `plan.ts` and `watch.ts` were. `main()` now parses, resolves and validates, then hands a resolved `ExportPlan` to `executeExport`, which renders once and writes each requested output. The rules that live there had no direct coverage while they sat at the bottom of a 264-line function behind a `parseArgs` call: the shared render happens **once** even when both modes are requested; the source stamp is earned by the **first** output that lands (so a WeasyPrint failure in `--mode pdf,html` cannot leave the exported HTML and its own source disagreeing about the document's date); the revision *bump* waits for **every** output, so both artifacts carry the same pre-bump revision; and `--strict` is judged after the output is written, never instead of it.

**Watch loop** (`watch.ts`) — `--watch`, extracted from `main()`'s file for the same reason `plan.ts` was: it was a closure nothing could reach. `startWatch(inputFile, deps)` takes the export itself, the directory watcher and the file read as injected dependencies and returns a handle, so the four rules that make it work are testable without a disk or a WeasyPrint run — the **self-write guard** (the export stamps the document it watches, so `main()` returns exactly what it wrote and a change matching that byte-for-byte is ours, never a reason to re-run; a timing-based guard would instead drop the edit you made *during* an export), the debounce that collapses an editor's multi-step save, the queue that runs a mid-export change once *after* it rather than concurrently or not at all, and the promise that a failed run never ends the watch. It watches the **directory**, not the file: `writeFileAtomic` and most editors replace a file by renaming a new one over it, which silently detaches an inode-bound watcher. What stays in `index.ts` is only what cannot be tested — the real export, the signal handlers, and blocking the process.

**PDF summary** (`pdfinfo.ts`) — `countPdfPages` reads the page-tree root's `/Count`, falling back to counting `/Type /Page` dictionaries, and returns **null** when neither can be found. WeasyPrint Flate-compresses its object streams, so on its own output *none* of those markers exist as plain bytes — the scan inflates every deflate stream first (bounded, best-effort, non-deflate streams skipped), which is the only reason a page count appears at all. `summarizePdf` then omits the page count rather than printing a wrong one. The earlier version scanned only the last 512 KB and always returned a number, so long documents silently under-reported.

**Config** (`config.ts`) — tool-level `CONFIG` only (DPI, timeout, JPEG quality, render concurrency, MIME/raster/alert-color tables). Env vars `EXPORT_PDF_DPI`, `EXPORT_PDF_TIMEOUT_MS`, `EXPORT_PDF_IMAGE_QUALITY`, `EXPORT_PDF_CONCURRENCY` override it via `applyEnvOverrides`. No brand data lives here anymore.

**Cover override slots** — every cover frontmatter key reaches a theme only if that theme's `html/cover-page.html` renders the matching token; a missing slot fails silently (this is how `Cover Slogan` was inert on ten themes and `Cover Address` on five until 2026-08-20). `src/tests/cover.test.ts` asserts the full slot set per theme. Note the audit trap: the templates list their own tokens in a header comment, so any grep-based check must strip comments and the standalone-preview `<script>` block before deciding a slot exists. `Cover Footer Logo` drives both `{{LOGO_IMG}}` and `{{LOGO_DARK_IMG}}`, since light-background layouts (markedapp-byword, witex) render the dark variant.

**Cover title colour** — every theme's `cover.css` must express title/subtitle/rule colours as `var(--cover-title-color, <own value>)`; `buildCoverCss` sets that property on `.cover-page` for the `Cover Title Color` frontmatter key and leaves it unset otherwise. Themes draw the title's rule very differently (bottom border, full box, left bar, `::after` strip) and each renders through its own layout class (`.cover-l4`, `.cover-mx`, …) that outranks a bare `.cover-title` selector, so the inherited custom property — not override rules — is what reaches them all. A per-theme test in `src/tests/cover.test.ts` fails the build if a theme hardcodes one of those colours.

**Theme search path** (`theme.ts`) — `--theme` always accepted a directory; what `--theme-path` / `EXPORT_THEME_PATH` add is *discovery*. `setThemeRoots` installs extra roots (each holding one directory per theme, like `themes/`), `listThemeEntries()` reports every discoverable theme with its directory and whether it is `builtin` or `external`, and `resolveThemeDir` searches external roots **before** the bundled ones so an external theme shadows a built-in of the same name — deliberate, since registering a folder called `default` is how you override the bundled one, and logged so it is never silent. Roots are installed by `applyThemeRoots` inside `parseArgs`, *before* the `--list-themes` / `--list-styles` pre-pass: listing themes without the roots applied would print a different set from the one the very next export resolves against. This is a CLI concept rather than an editor setting because the terminal, the VS Code extension and anything else driving the tool have to agree about which themes exist.

**Themes** (`theme.ts` + `themes/<name>/theme.json`) — a theme is a brand package: logos, fonts, CSS, cover/revision HTML templates, colour `palettes`, and named cover `styles`. `loadTheme(nameOrPath)` reads the declarative manifest, resolves every asset path to absolute, validates required files exist (exit 3), computes each style's gradient + main colour from its palette ref + overlay, and resolves fonts (literal `url`, or a named `env` var). Typography (`fontFamily`, `fontSize`) and `background` from the manifest are injected as CSS variables (`--font-body`, `--fs-h1`…, `--page-bg`) by `buildThemeVarsCss` in `css.ts`, plus `@page`-safe tokens (`{{PAGE_FONT}}`, `{{PAGE_BG}}`) in `buildPageCss`; the theme CSS references these. **`buildThemeVarsCss` also emits every palette as `--<slug>-<stop>` CSS variables plus a `--gradient-<slug>` per palette** (slug = lowercase palette name) — so `theme.json` is the single source of truth for brand colour and a theme's CSS must never restate hex values. **A palette's stop names are not its document roles**: a ramp authored for on-screen use often puts a pale tint at `main`, which washes out printed headings, table headers and cover gradients. `theme.json`'s optional **`paletteRoles`** map names which stop plays each document role (`main`, `light`) per palette — resolved by `roleColor` in `theme.ts`, defaulting to the identically-named stop, so themes without the key are unaffected. `modern` is the only theme that uses it today (every fruit palette maps `main` → its `dark` stop). The emitted CSS variables still carry the manifest's values verbatim; only the exporter's choice of stop differs. The active theme is a singleton (`setActiveTheme` in `main()`, lazy `getActiveTheme()` elsewhere); `EXPORT_PDF_LOGO[_WHITE]` override its logos, as does the `Logo` frontmatter key via `applyLogoOverride` (a name from the manifest's optional `logos` map, or a path; unknown names exit 3). Selection precedence in `main()`: `--theme` → `Theme` frontmatter → `EXPORT_THEME` → `default` (the brand-neutral built-in theme). `theme.ts` also owns per-document **style** resolution (`resolveStyle`, `resolveStyleMainColor`, `buildStyleOverrideCss`), chosen by the `Style` frontmatter key (named style or `{Color, Image, Position}` object). A named style may additionally carry `fontFamily`/`background`/`cssVars`/`fontImport`: `applyStyleOverrides(style)` is called in `main()` right after `setActiveTheme` to overlay the style's font/background onto the singleton *before* `buildThemeVarsCss`/`buildPageCss` run (they bake those into `@page`, so a late CSS-var can't reach them), while `buildStyleOverrideCss` — injected last in `<head>` — emits the style's `--brand-main`, extra `cssVars`, and `@import` web-font. This is what lets one theme host several looks as styles (`jasonm23`/`mixu`/`solarized`). Built-in theme names match the `themes/` subfolder case-insensitively.

**Preview kit** (`preview-kit.ts`, `preview-css.ts`, `preview-plugin.ts`) — `--preview-kit <dir>` writes live-preview stylesheets for every theme × style (plus `_base` for no `Style` and `_unknown` for a name the theme lacks, which the export tints with the default palette), and `--preview-format mpe` a `.crossnote/parser.js` for Markdown Preview Enhanced. Five rules. **The CSS is the export's own**: `buildPreviewCss` calls the same builders `buildHtmlExportPipeline` does, in its `<head>` order, and `readLocalStylesheet` is the export's stylesheet reader split out of `inlineLocalStylesheet` (with `keepIconImports`, since a preview has no document to scan for icons) — never add a hand-written preview stylesheet. **It is scoped, because a preview is someone else's page** (`preview-css.ts`): every rule is rewritten under `#pme-preview` — `html`/`body`/`:root` (and `body.html-export`) become the wrapper, `.github-markdown-body`/`.markdown-body`/`.github-markdown-content` become `.pme-body`/`.pme-content`, and a selector starting `.code-line` is confined to `pre` — then `PREVIEW_RESET_CSS` (`all: revert` inside the wrapper, SVG and KaTeX excepted) goes first. Both halves come from a real failure: VS Code puts `class="code-line"` on every block element including `table`/`tr`/`td`, so the themes' bare `.code-line { display: inline-block; width: 100% }` stacked every table cell, and the GitHub-styles extension scopes its dark CSS to `.github-markdown-body` — the export's own wrapper class — so its table rules outranked the theme's. The id outranks class-only third-party rules for properties the theme sets; the reset covers the ones it does not. Also: `@import`s lifted to the front, `@page` dropped, dark `prefers-color-scheme` blocks dropped and light ones unwrapped, and `previewPageCss` paints every ancestor of the wrapper (`:has(#pme-preview)`) with the page background. **A preview pane is narrow, so nothing may widen the page**: each outermost table is boxed in a `.pme-scroll` that scrolls on its own — in VS Code by `SCROLL_OPEN`/`SCROLL_CLOSE` *tokens* inserted in the core rule, never by post-processing `renderer.render` (Mermaid, Marp and GitHub-styles all replace `render`, and one does not call the one it replaced, so a wrapper there vanished in the real editor), and in MPE by `containWideContent` on the HTML string. A table another extension inserts after our core rule (YAML Preamble's frontmatter table) is caught by `.pme-content > table { display: block; overflow-x: auto }`, and `.katex-display` gets the same. Every such box is `position: relative`: KaTeX's hidden MathML copy is absolutely positioned, and in an unpositioned box a formula inside a table cell escapes the box's clipping and widens the page anyway. Reproduce preview bugs with the user's *real* preview extensions — `markdown.api.render` in an extension host plus their `markdown.previewStyles` in a dark-scheme browser page — not with plain markdown-it, which has neither the scroll-sync classes nor the competing CSS. **Each style reloads its theme** before `applyStyleOverrides`, which mutates the singleton — a test compares every jasonm23/mixu/solarized style against a fresh build. **`preview-plugin.ts` has zero imports**, because the one compiled file runs in three hosts: the CLI copies it into the kit, the VS Code extension `require`s that copy (so the extension has no second implementation of theme selection), and it is inlined into MPE's `parser.js`, which crossnote evaluates as a single expression inside a QuickJS WASM sandbox with no `require`/`process`/fs. Selection mirrors `resolveThemeName` and `resolveThemeDir` aliasing, and themes only documents with a top-level `Mode`/`Theme`/`Style`. **MPE specifics, each verified in crossnote's source**: `@import "x.css"` is dropped unless `enableScriptExecution`, so CSS is embedded; the marker naming the stylesheet is appended at the *end* of the markdown (an earlier line would shift MPE's scroll-sync line numbers); the `<style>` is appended *after* the content (DOMPurify hoists a leading `<style>` into a discarded head); and `writeMpeParser` replaces only its own file or MPE's inert default template, exiting 2 otherwise. The extension side (`vscode-extension/src/preview.ts`) contributes `markdown.markdownItPlugins`, regenerates the kit in `globalStorage` on activation and on theme-path/CLI/env setting changes, and re-resolves the stylesheet at render time because VS Code caches tokens per document; `markdown.preview.refresh` clears that cache.

**Question-answering surfaces** — `--inspect` (`describeDocument` in `index.ts`) prints the *resolved* frontmatter as JSON and stops: reads the document, renders nothing, writes nothing, and returns before the theme is loaded. `--list-themes --json` / `--list-styles --json` do the same for the theme catalogue, and `--check-setup --json` (`setup-status.ts`) for the runtime dependencies — the extension builds its one install question from it. That one is deliberately its own flag rather than `--setup --dry-run`: the extension asks it of whatever CLI it resolves, an older CLI ignores `--dry-run` next to `--setup` and would install everything on what was meant to be a question, while an unknown flag is refused and reads as "cannot tell". They exist because tooling has to know things about a document *before* acting on it — the VS Code extension asks whether the revision it is about to release already carries a note, and only prompts when it does not. Without them the editor would need its own YAML reader and theme resolver, which is a second answer to "what does this document say" living one refactor away from disagreeing with the first. `--inspect` returns the resolved view on purpose (`Mode: pdf, html` normalised, `resolveRevision`'s precedence applied, `isReleasedStatus` so `Vrijgegeven` counts) — a caller reading the file itself would have to re-implement all three.

**Release notes** — `--release-note <text>` sets the `Remarks` of the **outgoing** revision: the current last `Revisions` row, describing the work being signed off, which is the row the cover's revision table shows. `setLastRevisionRemarks` must run *before* `appendRevisionEntry`, or it would fill in the fresh row `--release` appends for the next revision — in which nothing has happened yet. It is a usage error without `--release`, because a note with nothing to attach it to would otherwise vanish while the export looked like it succeeded. Both frontmatter shapes are handled and the document's own key casing is kept.

**Scaffolding** — `frontmatterTemplate(today, answers?)` is the one implementation of answers → frontmatter, reached from the CLI by `--init [--answers <file.json>]` and from the extension's new-document wizard through that same flag. Answered values go through `yamlScalar`, which quotes only when YAML requires it: the default `--init` output stays byte-identical (people read it as documentation), while a title with a colon, an author with a comma inside a flow mapping, or a status of `No` are all protected. Answers arrive in a *file* rather than on the command line because a title and an author are free text a person types, and putting that through argv quoting on three platforms is a bug waiting to happen. **The extension keeps its own copy of the placeholder template** (`vscode-extension/src/core.ts`) — that is deliberate, guarded by a key-comparison test in `frontmatter.test.ts`, and the reason is that `insertFrontmatter` edits an *unsaved editor buffer* and must keep working when the CLI cannot be resolved. The wizard, which creates a real file, goes through the CLI instead.

**Error/exit conventions** — throw `ExitError(message, code)` from `errors.ts` for controlled exits; `main().catch` maps it to the documented exit codes (0 ok · 1 unexpected · 2 CLI usage · 3 file/asset not found · 4 WeasyPrint · 5 network). Use `log()` / `logResult()` from `logger.ts` (respects `--quiet`) rather than bare `console.log` for pipeline progress.

## Conventions

- CommonJS output (`tsconfig` module/moduleResolution: `nodenext`, which emits CJS because `package.json` has no `"type": "module"`), strict TypeScript, Node ≥ 20.9 (`engines.node`; the floor moved off 18 when sharp 0.35 did — CI exercises 20 and 22). Source is `src/`, compiled to `dist/` — never edit `dist/` by hand.
- **Every write that can land on a file the user owns goes through `writeFileAtomic` (`fsutil.ts`), never `fs.writeFileSync`.** That covers the source-markdown mutations (`updateFrontmatterDates`, `bumpRevisionAfterExport`, `cleanSourceTocAttrs`) and the HTML export output. `writeFileSync` truncates before it writes, so an interrupted export would leave the principal's own document empty — and the VS Code extension runs the export on every save. Only the transient WeasyPrint temp file writes directly.
- **Never write an HTML attribute pattern by hand — use `attributes.ts`.** `attrOf` / `setAttr` / `attrValues` / `findTags` / `tagWithAttrValue` are the only sanctioned way to read or rewrite an attribute. Two rules are baked into them, each learned from a shipped bug: all three quoting spellings (`html: true` is on, so a document may hand-write `src='x'` or `src=x`, and a pattern that knows only the double-quoted form markdown emits silently does nothing to the others), and a **leading `\s`** so an attribute name is matched whole. Without that second rule `src=` also matches the tail of `data-src=`: `<img data-src="lazy.png">` was read as an image reference (a spurious "Image not found", exit 6 under `--strict`), and on a tag carrying both, the inlined data URI was written into `data-src` while the real `src` kept pointing at a local file the exported HTML could no longer reach. That bug was found and fixed five separate times in three modules before the sixth copy was consolidated here; `src/tests/attributes.test.ts` is what keeps it consolidated.
- **A degraded fetch never reaches the disk cache.** `inlineCssRecursive` / `inlineFontsInCss` return `{ css, complete }`, and `buildIconStylesheet` writes an entry only when `complete`. Every failure path in those functions *removes* what it could not fetch and returns normally, which reads as success to a caller that only looks at the string — and the cache is permanent, has no expiry, and is trusted on the next read. Writing a degraded copy turned one transient network blip into a silently wrong export forever: later runs logged `(disk cache)`, made no request, and raised no warning, so not even `--strict` could see it. Entries are also stamped with `CACHE_SCHEMA` (`cache.ts`); bump it when the *shape* of a cached value changes, and stale-schema entries are swept on the next write.
- **A computed replacement always goes through `literal()` (`strings.ts`).** `String.replace`/`replaceAll` treat a *string* replacement as a template — `$&`, `` $` ``, `$'`, `$1` expand against the match — so a cover title of `Q1 $& Q2`, an `<img alt="a$&b">`, a third-party stylesheet or a Mermaid diagram echoed into an error block silently corrupts the output. `literal(value)` returns a function replacement, whose return value is inserted verbatim. `src/tests/strings.test.ts` locks this down for both template loaders.
- **`parseArgs` never calls `process.exit` and never writes to the console.** Every exit path throws `ExitError`, including `--help`/`--version`/`--list-*`, which use exit code 0; `main().catch` is the single place that terminates the process, and sends code 0 to stdout and everything else to stderr. Flags that print and stop are resolved in a pre-pass over the whole argv (`handleImmediateFlags`), so `--theme x --list-styles` and `--list-styles --theme x` agree. **Both the pre-pass and the main loop split argv through the one `tokenize`**, which pairs each value-taking flag with the token after it and folds `--flag=value` into the same shape — so `VALUE_FLAGS` is the single list of which options take a value. The main loop used to re-implement that with fourteen `startsWith('--x=')` branches beside the spaced forms, three lists to keep in agreement by hand; `tokenize` exists because they once did not agree (`--output -h doc.md` printed the help text). A value on a boolean flag (`--quiet=true`) is a usage error rather than a silent accept. Mode strings are parsed once by the exported `parseModes`, shared by the CLI (which rejects unknown values) and `main()` (which warns, since there they came from frontmatter).
- **Nothing transient is written into the user's document directory.** The processed HTML goes to `startServer`'s `files` option and is served from memory; only `--mode debug` writes a copy, deliberately. An export that dies mid-run therefore leaves no litter, and no cleanup path can be skipped.
- **The WeasyPrint server is gated on a per-run capability token.** `startServer` serves the *user's own document directory*, so knowing the port must not be enough to read it: every request must be `/<token>/<path>` or it gets a 403 before any filesystem access. The token is a path prefix rather than a header so relative asset references inherit it with no rewriting; use the returned `urlFor()` rather than building the URL by hand.
- **Renderers that fan out over document matches must be bounded**, via `mapPool`/`createLimiter` (`concurrency.ts`) at `CONFIG.concurrency` (default 4, `EXPORT_PDF_CONCURRENCY`). Unbounded `Promise.all` over matches is how a diagram-heavy document opens one Chromium page, spawns one draw.io Electron process, or decodes one full-resolution image per match at once. draw.io gates at the CLI spawn rather than the caller, capped at 2, because each invocation is a whole Electron instance and one SVG-mode diagram already needs two (light + dark).
- **`index.ts` only runs `main()` under `require.main === module`**, so `main` itself and `renderDiagramsAndImages` / `buildHtmlPipeline` / `buildHtmlExportPipeline` can be imported by a test. `main({ argv })` takes its arguments rather than reading `process.argv`, which is what lets `src/tests/main.test.ts` drive whole exports in-process — output naming, the deferred source stamp, the release bump, and the `ExitError` exit codes — all in `--mode html`, which needs no WeasyPrint, no Chromium and no network. Same argument path the watch loop uses to re-run with the flags it started with. `src/tests/pipeline.test.ts` is the end-to-end suite: it runs the real three-stage sequence over `test-fixtures/pipeline/document.md`, asserts structural invariants, and diffs a normalised golden file (`expected-html-export.html`, with `<style>` bodies and `data:` URIs collapsed to byte counts so it stays reviewable). Regenerate with `UPDATE_GOLDEN=1 npm test` and read the diff — never regenerate to make a failure go away. The fixture deliberately has no Mermaid, draw.io, images or icon fonts, so the suite needs no Chromium, no draw.io app and no network; adding any of those to it would make CI fetch a font on a cold runner.
- **The VS Code extension's editor-free logic lives in `vscode-extension/src/core.ts`.** `extension.ts` imports `vscode` at its top, so nothing in it can be loaded by a `node --test` process — which is how ~670 lines shipped with no test at all, two of them carrying an "exported for testing" comment. Frontmatter reading (what makes a save trigger an export), the CLI identity check, `quoteArg` and `EXIT_MESSAGES` are plain string and filesystem work and belong in `core.ts`; `extension.ts` keeps only what touches the editor. `vscode-extension/npm test` runs `out/tests/core.test.js` by explicit path (no glob — `cmd.exe` does not expand one), and CI runs it beside the compile and lint. Add pure logic there, not to `extension.ts`.
